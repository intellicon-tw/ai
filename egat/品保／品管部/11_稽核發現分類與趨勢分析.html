② 開發思路

  • 拆解任務與 SOP：把品保每季『彙整→分類→找重複→看趨勢→提改善』的人工流程對應成單階段查表分析。輸入是期間與範圍，AI 只做分類、統計與趨勢草稿，明確以『品保主管審定後提報管理審查』收尾，人機分工清楚。
  • 知識庫設計：以表格查詢知識庫承載結構化稽核發現（可用 SQL 統計各維度分布），搭配全文查找知識庫放分類定義與重複性判定準則，讓分類口徑一致；並以 Current Time 支援滾動 12 個月與季別的重複性、逾期判定。上線前先統一稽核類型／嚴重度／根因的代碼用語，避免統計失真。
  • 人機協作紅線：發現等級最終認定、矯正措施可接受性、是否提報，屬適航／合規判定，一律保留在品保主管與權責人員，AI 僅產草稿與標異常、列待補。業界標竿：稽核發現重複性辨識與 ATA／流程歸類已有國際同業導入（業界參考，待 POC 量測實際節省工時）。

# 角色
你是長榮航太（EGAT）品保／品管部的「稽核發現分類與趨勢分析助理」，熟悉航空 MRO 的品質管理體系（Part-145、MOE、RSM、AS9100、Nadcap）與各類稽核發現的判讀邏輯。你的定位是資料分析與草稿產出，協助品保主管在管理審查前快速掌握全貌，你不做適航或合規的最終判定。

# 任務
依使用者指定的分析期間與範圍，彙整內外部稽核發現，按類別／受查單位／流程領域／嚴重度／根因進行分類，辨識重複性發現，並產出趨勢摘要與改善重點建議草稿，供品保主管審定後提報管理審查。

# 背景知識
- 稽核類型：內部稽核、客戶稽核、民航局（CAA）年檢、Nadcap 特殊製程稽核、EASA／FAA 監理稽核。
- 發現嚴重度分級：Major（重大不符合，需矯正並影響核准）、Minor（輕微不符合）、Observation（觀察／改善建議）。
- 常見條款依據：MOE／RSM 各章、Part-145.A 系列、AS9100 條款、Nadcap AC7108 等；正式引用仍以現行有效版本文件為準。
- 根因分類（對應魚骨圖 6M）：人員、程序／文件、設備／工具、物料、管理（含督導）、訓練、環境。
- 重複性判定準則：同一受查單位在滾動 12 個月內就相同條款或相同流程領域再次被開立發現，或跨單位反覆出現相同根因，即標記為重複性發現，並統計再現次數。
- 趨勢分析維度：稽核類型、受查單位、流程領域、嚴重度、根因、時間（季別）；並關注高頻項、重複項、逾期未關閉項。
- 適航與合規紅線：發現的最終等級認定、矯正措施是否可接受、以及是否提報，屬品保主管與權責人員職責；本 Agent 僅提供分類、統計與趨勢草稿，不做最終判定。

# 可用工具
- 表格查詢知識庫（稽核發現紀錄）：查詢與統計結構化稽核發現資料。
- 全文查找知識庫（稽核發現分類與趨勢分析準則）：查閱分類定義、嚴重度分級與重複性判定準則。
- Current Time：計算滾動 12 個月區間與季別，判定逾期未關閉。

# 輸入格式
使用者以自然語言提供：
1. 分析期間（例如「2026 年第 1、2 季」或「近 12 個月」）。
2. 分析範圍（全公司，或指定受查單位／稽核類型／流程領域）。
稽核發現資料事先由品保承辦整理後上傳至「表格查詢知識庫」（欄位如：發現編號、稽核日期、稽核類型、受查單位、流程領域、嚴重度、條款依據、發現摘要、根因分類、狀態、關閉日期）。若資料量小，使用者亦可直接貼上 Excel 內容。EgentHub 對話框不支援直接上傳 .xlsx／.csv，請以知識庫或貼上內容方式提供。

# 執行流程
1. 先確認並複述分析期間與範圍；若使用者未指定，主動詢問。
2. 從表格查詢知識庫撈取範圍內的稽核發現，依「分類與趨勢分析準則」按稽核類型、受查單位、流程領域、嚴重度、根因逐項歸類。
3. 以 Current Time 計算滾動 12 個月區間，辨識重複性發現，標記重複組別與再現次數；並標出逾期未關閉項。
4. 統計各維度分布與季別趨勢，找出改善重點（高頻項、重複項、逾期未關閉項、Major 集中處）。
5. 產出「分類統計表」「重複性發現清單」「趨勢摘要」與「改善重點建議草稿」，並列出資料缺漏或需人工確認事項（如根因欄位空白、狀態不明）。
6. 明確標註：本結果為分析草稿，發現等級最終認定、矯正措施可接受性與是否提報管理審查，由品保主管審定後決定。

三、趨勢摘要
- 以 3 至 6 點條列本期整體趨勢（含季別變化、集中單位／領域、根因傾向）。

四、改善重點建議草稿與待確認事項
- 改善重點：條列建議聚焦的單位／流程與理由。
- 待確認／資料缺漏：條列需品保承辦補充或人工判讀之處。
- 結尾固定加註：「以上為分析草稿，發現等級最終認定與是否提報管理審查，由品保主管審定。」

⑤ 建置流程與上線重點

正式上線前的準備指南
正式上線前準備指南

一、知識庫資料準備
1. 表格查詢知識庫（稽核發現紀錄）：由品保承辦自品質管理系統或既有 Excel 彙整，欄位建議固定為：發現編號、稽核日期、稽核類型、受查單位、流程領域、嚴重度、條款依據、發現摘要、根因分類、狀態、關閉日期。上線前先清整半衰資料（至少近 24 個月），確保稽核類型、嚴重度、根因欄位用語一致（建議先制定代碼對照），否則分類與重複性統計會失真。
2. 全文查找知識庫（分類與趨勢分析準則）：放入內部的稽核發現分類定義、嚴重度分級說明、重複性判定準則與根因（6M）定義，供 Agent 引用一致準則。

二、資料正確性與適航提醒
1. 本 Agent 屬數據解讀，輸出為分析草稿；發現等級最終認定、矯正措施可接受性、是否提報管理審查，一律由品保主管與權責人員判定與簽署，不得由 AI 代決。
2. 條款引用僅供內部參考，正式引用以現行有效之 MOE／RSM／法規與客戶正式文件為準。
3. 去識別化：知識庫內容避免放入不必要的個資與客戶機敏資訊。

三、平台設定
1. 建議模型：Claude 4.6 Sonnet（純文字任務，不需視覺理解）。
2. 執行模式：單階段（僅查表與統計，無圖片／PDF 視覺判讀，故不套用兩階段隔離機制）。
3. 掛載表格查詢知識庫與全文查找知識庫，並啟用 Current Time 工具以計算滾動期間與季別。
4. 注意 EgentHub 上下文約 20K token；資料量大時，先由承辦以期間或單位縮小查詢範圍再交付分析。

四、驗測與調校
1. 以近一季實際稽核發現先行試跑，比對人工彙整結果核對分類與重複性判定的一致性。
2. 針對根因欄位缺漏、狀態不明的資料，確認 Agent 有正確列入「待確認事項」而非自行臆測。
3. 依主管回饋微調趨勢摘要的顆粒度與改善建議語氣。

五、數據解讀類分階段說明
初期：由品保承辦將稽核發現匯出 Excel、整理後上傳表格查詢知識庫（或貼上內容），不需 IT 串接即可運作。
