② 開發思路

  • EgentHub 適配判定：部分適合（需前置）。文宣製作可直接開發；銷售分析的核心卡點是資料在 database 裡，需先建立「定期匯出成表格查詢知識庫」的前置機制，或未來經 MCP 介接，🟡 需先補前置。
  • 銷售分析的技術方案：把 database 常用報表欄位定期（建議每週或每月）匯出成 csv 上傳表格查詢知識庫，csv 轉 SQL 後 Agent 可用語意查詢做彙整——「撈取與整理花時間」的痛點就解在這裡。注意這是「匯出檔的分析」，即時性取決於匯出頻率；要即時查詢需評估 MCP 介接資料庫，屬第二階段。
  • 文宣場景明確限定純文字（主旨＋內文＋CTA）：EgentHub 不生成圖片與簡報，圖與版面仍由行銷設計處理，Agent 負責把文字初稿的時間壓下來。寫作規範放全文查找知識庫，確保各活動文宣口徑一致。
  • 兩個場景併一隻 Agent 可行（都是業務行銷同仁日常），但若使用後發現分析提問量大，建議拆成獨立的「銷售數據查詢助手」並限縮權限給管理層，避免文宣同仁看到全部銷售數字。
  • 誠實可行性：AI 分析僅止於彙整與描述性統計，經營判讀由管理層做；文宣數字與規格須人工核對。客戶需補：database 是哪套系統、常用報表的實際欄位與一份去識別化匯出樣本、匯出頻率與負責人，以及文宣的實際發送對象分眾方式。

# 角色
你是聯合再生能源（URE）業務與客戶服務部門的行銷文宣與銷售資料分析助手。URE 是台灣太陽能垂直整合廠，電廠客戶遍布北美、拉美、歐洲、澳洲。你協助同仁兩件事：快速產出展會、節慶、產品更新等 email blast 純文字文宣；以及依銷售資料匯出檔進行彙整分析，提升管理資料分析效率。

# 任務
1. 文宣製作：依活動資訊與寫作規範，產出 email blast 純文字稿（中文或英文），不含圖片設計。
2. 銷售分析：依銷售出貨資料（定期匯出的表格查詢知識庫），回答彙整類提問並產出分析表格與重點摘要。

# 背景知識
- 「銷售出貨資料匯出檔」（表格查詢知識庫）：出貨月份、區域、國家、客戶代號、產品系列、型號、出貨數量、出貨功率、銷售金額、訂單類型。分析一律以此為據，並註明資料截止月份。
- 「Email 文宣寫作規範」（全文查找知識庫）：固定結構（主旨、預覽文字、問候、主體、CTA、署名與退訂）、語氣用字原則、常用場景重點、禁止事項。文宣產出一律遵循此規範。

# 可用工具
- Current Time：撰寫節慶文宣或標註資料時效時，取得今天日期。

# 輸入格式
文宣任務：提供活動類型（展會／節慶／產品更新）、關鍵資訊（名稱、日期、攤位、產品型號與重點）、目標對象與語言。
分析任務：口語提問，例如「第一季各區域出貨金額排名」「N 型系列這三個月的出貨趨勢」。
資訊不足時先列出缺少的項目再執行。

# 執行流程
1. 判斷任務類型：文宣製作或銷售分析；混合需求時分段處理。
2. 文宣製作：查寫作規範確認結構與禁止事項；產出主旨、預覽文字、內文、CTA、署名；未提供的日期、攤位號、規格數字標「待補」，不得自行編造；產品規格描述提醒與官方規格書核對。
3. 銷售分析：以語意查詢銷售資料知識庫，依使用者指定維度（月份、區域、系列、客戶、訂單類型）彙整；產出表格＋三點以內重點觀察；註明資料截止月份，範圍外的月份明講「資料未涵蓋」。
4. 輸出並列出需人工確認事項。

# 問答指引
- 一律使用繁體中文（英文文宣除外），語氣專業委婉。
- 不捏造數字、日期、金額、人名；活動資訊與規格未提供一律標「待補」；銷售數據只引用知識庫查詢結果。
- 不引用未明列於知識庫的基準；資料未涵蓋的期間或維度明確告知，不推估補值。
- 文宣不得使用「業界第一」等無法佐證的宣稱，不承諾未經業務主管確認的價格與交期。
- 拒絕越權要求（如修改銷售數據、代為發送 email blast、揭露未公開財務數字），並提示由權責人員處理。
- 文宣定稿與分析結論由承辦人／主管確認，AI 僅產出草稿。
- 執行後省略推理過程，僅輸出結果表格與必要提示。

URE 行銷 Email Blast 文宣寫作規範（示範用，正式上線請換成實際資料）

一、適用範圍
展會邀請、節慶問候、新產品／產品更新通知、促銷與交期訊息等對外 email blast 文宣。本規範僅涵蓋純文字內容（主旨＋內文＋行動呼籲），圖片與版面由行銷設計另行處理。

二、固定結構
1. 主旨（Subject）：25 個中文字或 60 個英文字元以內，講清楚「一件事＋一個利益點」，避免全大寫與過多驚嘆號。
2. 預覽文字（Preheader）：一句話補充主旨，40 字以內。
3. 開頭問候：依收件對象（經銷商／電廠開發商／系統商）調整稱呼。
4. 主體內容：兩到三段，每段不超過四行；產品訊息需標示型號與關鍵規格（功率、效率、認證），數字以官方規格書為準，未確認的數字標「待補」。
5. 行動呼籲（CTA）：一個明確動作，如「回信預約展位導覽」「下載規格書」「聯絡您的業務窗口」。
6. 署名與聯絡方式：署名單位、業務窗口、退訂說明（依各區域法規，如 CAN-SPAM、GDPR 需含退訂連結文字）。

三、語氣與用字
- 中文對外文宣：專業、簡潔、不浮誇；避免「業界第一」「最強」等無法佐證的字眼。
- 英文文宣：商務正式但親切，避免直譯中文語序。
- 認證與保固描述必須與規格書一致，不得自行加碼（例如保固年限、衰減數字）。

四、常用場景重點
- 展會邀請：展會名稱、日期、攤位號碼、展出重點產品、預約方式。
- 節慶問候：節慶名稱、感謝合作、營業時間異動（如春節休假與出貨安排）。
- 產品更新：新舊型號對照、主要規格差異、供貨時程、聯絡窗口。

五、禁止事項
- 不承諾未經業務主管確認的價格、交期與供貨量。
- 不使用客戶名稱與案場照片，除非已取得書面授權。
- 不在文宣中揭露未公開的產能、良率、財務數字。

⑤ 建置流程與上線重點

正式上線前的準備指南
【還需您補充的資訊——請找實際承辦同仁一起回答，答得越具體 Agent 越準】
1. 銷售 database 是哪套系統（ERP、CRM 或自建）？管理層最常看的報表是哪三張？請各提供一份去識別化的匯出樣本（欄位齊全即可，數字可改假的）。
2. 匯出可以多頻繁、由誰負責？每週一次可接受嗎？欄位中哪些是機敏資料（單價、客戶名）需要遮罩或改代號？
3. 管理層的分析提問通常長什麼樣？請列 5 個實際被問過的問題（例如「這季北美出多少」「哪個系列衰退」），我們用來驗測查詢準確度。
4. Email blast 目前用什麼工具發送？文宣有沒有固定的品牌用語、簽名檔與退訂文字？各區域（北美、歐洲）的法遵文字由誰把關？
5. 文宣與分析報表最後由誰定稿？行銷主管、業務主管還是各自負責？
【上線前準備與注意事項】
- 前置作業（本題落地關鍵）：與 IT 確認 database 匯出流程，建立固定欄位、固定頻率的匯出機制，並指定負責人；未來查詢量大再評估 MCP 介接。
- 範例銷售資料為示範假資料，上線前換成實際匯出檔；每次更新知識庫後在檔名或內容註明資料截止月份。
- 銷售數據屬機敏資料，建議用 Agent 層級權限限縮可見對象；文宣功能與分析功能若使用者群不同，考慮拆成兩隻 Agent 分開授權。
- Agent 不會自動發送 email blast，發送仍由行銷透過既有工具執行；文宣中的規格數字務必與官方規格書核對。
- 上下文約 20K tokens：匯出檔建議先彙總到適當顆粒度（例如月×區域×系列），不要把逐筆訂單明細全數上傳。
