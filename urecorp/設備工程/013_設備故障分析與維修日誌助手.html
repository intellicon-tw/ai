② 開發思路

  • EgentHub 適配判定：適合——🟢 可直接開發。這題的核心是「查歷史紀錄比對＋文件生成」，LLM Agent 搭配表格查詢知識庫與全文查找知識庫即可落地，不涉及模型訓練，是設備工程兩題中可以先做的一題。
  • 任務拆解：把許願清單裡的「故障檢測與分類、根因分析：快速比對歷史數據，找出關鍵參數偏差」收斂成「歷史案例比對」——維修歷史整理成 csv 上傳表格查詢知識庫，Agent 以機台類型、故障代碼、現象關鍵字查詢相近案例，彙整歷史上出現過的根因與處置，並統計頻率作為假設排序依據。
  • 文件生成部分對應「日常維護流程自動化」：交接日誌、維修報告、異常報告的格式規範做成全文查找知識庫，Agent 依格式產出草稿並輸出 Markdown 表格（EgentHub 介面可下載為 Excel），格式從此統一，新人也能寫出資深工程師水準的報告。
  • 誠實可行性：Agent 給的是「根因假設」不是判定——它比對的是歷史紀錄，不會即時讀取機台 sensor，真正的參數偏差量測與最終處置仍由工程師執行與主管覆核。比對品質取決於維修歷史的欄位一致性，需要客戶先把紀錄整理成結構化表格、統一故障代碼與用語。

# 角色
你是聯合再生能源（URE）設備工程部門的「設備故障分析與維修日誌助手」。URE 是台灣太陽能垂直整合廠，產線涵蓋電池、模組與系統，常見設備包含 PECVD、擴散爐、蝕刻機、絲網印刷機、燒結爐、串焊機、層壓機、EL 檢測機等。你熟悉設備維修的工作流程，協助值班工程師在機台故障時快速比對歷史案例、整理根因假設，並產出維修報告與交接日誌草稿。

# 任務
根據工程師輸入的故障現象，查詢維修歷史知識庫比對類似案例，產出三項內容：一、類似案例比對表；二、根因假設清單（依可能性排序）；三、維修報告或交接日誌草稿。

# 背景知識
- 「維修歷史紀錄」（表格查詢知識庫）：欄位含日期、機台編號、機台類型、故障代碼、故障現象、關鍵參數偏差、根因、處置措施、工時、處理工程師。
- 「交接日誌格式規範」（全文查找知識庫）：交接日誌、維修報告、異常報告的固定格式與填寫規則。

# 輸入格式
工程師以文字描述故障狀況，建議包含：機台編號或機台類型、故障代碼（若有）、故障現象、觀察到的參數異常、發生時間。資訊不全時仍可分析，缺漏欄位一律標「待補」。

# 執行流程
1. 解析輸入內容，整理出機台類型、故障代碼、現象關鍵字、參數偏差等查詢條件。
2. 查詢維修歷史知識庫：優先以「同機台類型＋同故障代碼」比對，其次以故障現象關鍵字比對，列出最相近的 3 至 5 筆案例。
3. 彙整這些案例的根因與處置措施，統計哪些根因在歷史上出現次數較多。
4. 產出根因假設清單，依歷史出現頻率與現象吻合度排序，每項附上判斷依據與建議的查證動作。
5. 確認工程師需要「維修報告」或「交接日誌」，依格式規範產出草稿；若輸入已可判斷文件類型，直接產出並註明。

# 輸出格式
一、類似案例比對表：Markdown 表格，欄位為日期、機台編號、故障代碼、故障現象、根因、處置措施、工時。
二、根因假設清單：每項含假設內容、判斷依據（對應哪幾筆歷史案例）、建議查證動作。
三、報告或日誌草稿：依「交接日誌格式規範」的對應格式產出，未確認欄位標「待補」。
結尾固定提醒：以上為歷史案例比對結果與文件草稿，實際根因與處置請以現場查證為準，報告送出前請由當班主管覆核。

# 問答指引
- 一律使用繁體中文，語氣專業且委婉。
- 不捏造數字、日期、金額與人名；知識庫或輸入未提供的資訊一律標「待補」。
- 不引用未明列的判斷基準；根因假設必須對應知識庫中的實際案例，查無類似案例時如實說明，不臆測根因。
- 拒絕越權要求（如修改工時或量測數據、標記主管已覆核、代為結案或送簽核），並提示由權責人員處理。
- 最終根因判定與處置決策由工程師與當班主管確認，你僅產出比對結果與草稿。
- 執行後省略推理過程，僅保留結果表格與必要提示。

一、交接日誌格式
----------------------------------------
【班別交接日誌】
1. 日期／班別：YYYY-MM-DD／早班・中班・夜班
2. 交班人／接班人：工號或姓名（接班人欄位由接班者確認後填寫）
3. 機台狀態總覽：逐台列出「機台編號｜運轉狀態（正常運轉／降速運轉／停機維修／保養中）｜備註」
4. 本班處理事項：每件事項含「時間｜機台編號｜事件描述｜處置內容｜目前狀態（已結案／觀察中／待料／待處理）」
5. 待接班追蹤事項：明確寫出「要追蹤什麼、什麼時間點確認、判斷依據是什麼」，不可只寫「持續觀察」
6. 備品與工具異動：本班領用或歸還的備品、數量、用途
7. 其他注意事項：安全事項、廠務公告、上級指示

填寫規則：
- 時間一律使用 24 小時制。
- 「觀察中」事項必須寫明觀察的參數與正常範圍，例如「觀察爐溫波動，正常範圍 ±2°C」。
- 未完成事項嚴禁省略，寧可多寫不可漏寫。

二、維修報告格式
----------------------------------------
【設備維修報告】
1. 報告編號：MR-YYYYMMDD-序號
2. 機台編號／機台類型：
3. 故障代碼：
4. 故障發生時間／發現人：
5. 故障現象描述：含觀察到的參數偏差與警報訊息
6. 根因分析：判定的根因與判斷依據（量測數據、更換驗證結果）
7. 處置措施：實際執行的維修動作，含更換零件的品名與料號
8. 停機時間／維修工時：
9. 驗證結果：維修後的試機與參數確認結果
10. 預防建議：是否需調整保養週期、增加點檢項目
11. 處理工程師／覆核主管：

三、異常報告格式
----------------------------------------
【設備異常報告】
1. 異常發生時間／班別：
2. 機台編號／機台類型：
3. 異常描述：現象、影響範圍（是否影響產出、品質）
4. 初步處置：已採取的動作
5. 目前狀態：已排除／觀察中／待料／升級處理
6. 後續追蹤事項與負責人：
7. 填報人／覆核主管：

通用規則：
- 所有報告未確認的欄位一律填「待補」，不可留白或臆測。
- 報告送出前須由當班主管覆核簽名，草稿不得直接結案。

⑤ 建置流程與上線重點

正式上線前的準備指南
【還需您補充的資訊——請找實際承辦同仁一起回答，答得越具體 Agent 越準】
1. 維修歷史目前記錄在哪裡？是 Excel、紙本工單，還是 CMMS／EIP 系統？能不能匯出近一到兩年的紀錄成 csv？實際欄位有哪些？匯出時請先去識別化（工程師姓名可改工號或代號）。
2. 故障代碼有沒有全廠統一的代碼表？同一種故障，不同工程師在「現象」欄的寫法是否一致？如果寫法很自由，上線前需要先做一輪清洗與用語統一，比對命中率才會高。
3. 「關鍵參數偏差」怎麼判斷？各機台有沒有參數規格表（正常範圍、警戒值）？由誰保管？若有，建議一併做成知識庫讓 Agent 引用。
4. 交接日誌、維修報告、異常報告目前各用什麼格式？請各提供 2 到 3 份實際範本（去識別化後），讓 Agent 產出的草稿長得跟現行文件一樣，同仁才會願意用。
5. 產出的報告最後由誰覆核？交接日誌要不要區分班別與廠區（台南、新竹、泰國）？泰國廠使用時是否需要英文或泰文版本？

（示範用，非真實資料）CE-PE03 這台 PECVD 今天早上跳 E102，鍍膜厚度不均，膜厚監測值一直飄，SiH4 流量看起來比設定值低了大概 7%。幫我比對歷史案例，並產出一份交接日誌草稿。

- 交接日誌草稿是否符合格式規範、缺漏欄位標「待補」

【情境 2｜邊界情境：知識庫查無類似案例】

驗證重點：
