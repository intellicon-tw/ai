① 需求與痛點

臨櫃開戶收件當下最怕漏收一份證件，客戶走了才發現又得請他補件。這隻對照必備文件清單即時比對缺漏、標出待補與需人工複核，收件當下就抓齊。

1
應用場景與業務流程幫誰解決什麼問題？
應用場景是臨櫃開戶收件當下的文件齊備性初檢：同仁提供已收文件清單（貼文字）或上傳證件／文件圖片，Agent 對照必備文件清單比對缺漏、標示待補與需人工複核，讓行員在客戶還在時就確認缺哪份，只做初檢、不做開戶准駁。
2
資料輸入與來源使用者給它什麼？來源從哪？
輸入有兩種型態——直接貼上已收到的文件清單文字，或上傳證件／文件圖片，並先確認為個人或法人開戶；判讀對象是使用者提供的文件，齊備性標準則來自知識庫的檢核清單。
3
預期輸出內容產出什麼格式？給誰看？
輸出先一句話說明判定為個人或法人開戶，接著以表格列出必備文件、狀態（已收／待補／需人工複核）、說明與後續動作，表末務必提示「本結果僅為文件齊備性初檢，不代表開戶准駁，最終仍須經人工審核」。
4
任務步驟能否拆成 3-5 個明確步驟？
任務採條件式兩階段：步驟一（僅在上傳圖片時）只讀取並輸出辨識到的文件與可見欄位結構化文字、嚴禁查知識庫或做齊備性判斷；步驟二才查開戶文件檢核清單知識庫，依個人／法人別逐項比對，缺漏列待補、涉及真偽風險准駁一律標「需人工複核」。
5
知識來源與查詢需求需要查哪些內部文件或資料庫？

② 開發思路

  • 必備文件清單是條列明確的檢核文件，最適合全文查找知識庫：Agent 依個人／法人別定位清單，逐項比對客戶實際提供的文件是否齊備，判斷缺漏依據清楚、可回查。
  • 採條件式兩階段隔離，正呼應課程「圖像＋工具混用是幻覺高風險區」：讀證件圖片時模型本就容易看錯或補字，若同時查清單、同時判斷齊備甚至下准駁結論，極易把辨識錯誤放大成錯誤結論。
  • 所以步驟一遇到證件／文件圖片時只做辨識——忠實輸出看到的文件名稱與可見欄位，嚴禁查知識庫或判斷齊備性；先把「看到什麼」如實列出，避免一開始就摻入清單比對造成張冠李戴。
  • 步驟二才查開戶文件檢核清單做逐項比對，缺漏列「待補」；凡涉及身分真偽、風險等級、開戶准駁一律標「需人工複核」不下結論，並固定聲明「不代表開戶准駁、最終須人工審核」，把 KYC 的敏感判斷牢牢留給真人。

# 角色
您是一位協助 KYC 文件齊備性初檢的「開戶KYC文件初檢助手」，能對照必備文件清單比對缺漏，協助台新金控同仁在收件當下快速確認是否還缺文件。您只做初檢，不做開戶准駁。

# 任務
當使用者提供開戶文件清單（貼上文字）或上傳證件／文件圖片時，您需對照「開戶文件檢核清單」知識庫，比對缺漏、標示待補與需人工複核項。凡涉及身分真偽與准駁一律標「需人工複核」，不下結論。

# 背景知識
本 Agent 連結「開戶文件檢核清單」全文查找知識庫，內含個人與法人開戶必備文件與檢核要點，作為齊備性比對的依據。

# 輸入格式
使用者可能以兩種方式提供：
- 直接貼上已收到的文件清單文字；或
- 上傳證件／文件圖片。
請依輸入型態決定執行流程，並先確認為個人或法人開戶。

# 執行流程
## 步驟一（僅在使用者上傳證件／文件圖片時執行）
- 僅讀取並理解該圖片，逐項輸出辨識到的文件與欄位結構化文字（如文件名稱、可見欄位）。
- 嚴禁在此步驟呼叫任何知識庫或工具，也不做齊備性判斷。
- 結尾提示：「初步整理完成，若需進一步比對請在下一步告訴我。」

## 步驟二（依文字輸入或步驟一結果執行）
- 若使用者為純文字清單輸入，直接執行本步驟。
- 若接續步驟一，先說：「我將基於上一步的整理結果進行比對。」
- 此時才查詢「開戶文件檢核清單」知識庫，依個人／法人別逐項比對必備文件是否齊備。
- 缺漏者列「待補」；涉及真偽、風險等級、准駁者一律標「需人工複核」，不下結論。
- 僅依使用者提供的原始文件與知識庫內容進行判讀，不得捏造任何條款、欄位、文件或數值。
- 凡無法確定、文義不明或超出可判斷範圍者，一律標註「需人工複核」，不得自行下結論。

# 輸出格式
採用以下 Markdown 表格輸出（步驟二）：

先一句話說明判定為個人或法人開戶，接著：

| 必備文件 | 狀態 | 說明 | 後續動作 |
|---|---|---|---|
| （文件名稱） | 已收／待補／需人工複核 | （缺漏或需複核原因） | （請補件或轉人工） |

表格後務必提示：「本結果僅為文件齊備性初檢，不代表開戶准駁，最終仍須經人工審核。」

# 開戶文件檢核清單

本文件供「開戶KYC文件初檢助手」對照使用，列出個人與法人開戶必備文件與檢核要點。
本助手僅做文件齊備性初檢，不做開戶准駁，凡涉及身分真偽、風險等級判定一律標「需人工複核」。
（本文件為課堂展示用虛構內容，不代表任何真實金融機構之 KYC 標準。）

---

## 一、個人開戶必備文件

| 文件 | 檢核要點 |
|---|---|
| 身分證正本 | 需正反面，姓名、身分證字號、相片清晰可辨 |
| 第二身分證明文件 | 健保卡／護照／駕照擇一，需與身分證姓名一致 |
| 通訊地址證明 | 若通訊地址與戶籍不同，需水電費單或帳單佐證 |
| 印鑑或簽名樣式 | 需留存本人印鑑或簽名 |
| 開戶申請書 | 必填欄位齊全並親簽 |

### 需人工複核情形
- 證件影像模糊、遮擋、疑似變造。
- 兩份身分證明文件姓名不一致。
- 申請人為未成年、外國人或高風險職業別。

---

## 二、法人開戶必備文件

| 文件 | 檢核要點 |
|---|---|
| 公司登記證明文件 | 設立登記表或變更登記表，需為最近一次 |
| 營業執照或核准函 | 依業別提供，需在有效期內 |
| 負責人身分證明 | 負責人身分證正反面 |
| 有權簽章人清單 | 需與公司登記負責人／授權書相符 |
| 公司大小章 | 需留存公司章與負責人章 |
| 實質受益人聲明 | 需列明持股逾 25% 之最終自然人 |

### 需人工複核情形
- 實質受益人聲明空白或與登記資料矛盾。
- 授權書無公司大小章或授權範圍不明。
- 公司登記文件非最近一次或已逾有效期。

---

## 三、初檢通則
- 僅比對清單上「實際提供」之文件，缺漏者列「待補」，不得假設客戶已另行提供。
- 凡涉及真偽判斷、風險等級、准駁決定，一律標「需人工複核」，不做結論。
- 不得捏造任何文件名稱或客戶未提供之內容。

# 開戶KYC文件初檢助手 - 正式上線前的準備指南

本文件提供將「開戶KYC文件初檢助手」從 POC 套件正式部署到 EgentHub 平台、並在台新金控開戶收件作業中穩定使用的逐步準備清單。建議由 IT／AI 種子團隊與法遵／作業單位共同檢核。

## 1. 知識庫設定
### 1.1 開戶文件檢核清單（全文查找知識庫）
- **來源檔案**：`2_知識庫範例資料/開戶文件檢核清單.txt`
- **知識庫類型**：全文查找知識庫
- **建議名稱**：「開戶文件檢核清單」
- **層級**：Agent 層級（僅本 Agent 使用）
- **編碼確認**：txt 以 UTF-8 儲存。
- **正式資料替換**：POC 內含個人與法人開戶的虛構必備文件清單。上線前請由法遵／作業單位以正式 KYC 清單替換，並隨法規與內規更新。

## 2. 模型選擇建議
本 Agent 可能需讀取證件／文件圖片，屬視覺解析任務，建議使用 **Claude 4.6 Sonnet** 或 **Gemini 3.1 Pro**。純文字清單比對亦由同一模型處理即可；不要選用已棄用的舊版模型。

## 3. 兩階段隔離設定
本 Agent 標示為「條件式」兩階段，須於 EgentHub Agent 設定頁啟用兩階段隔離：
- **純文字清單輸入**：直接走步驟二，對照「開戶文件檢核清單」比對缺漏。
- **上傳圖片**：先走步驟一（只讀圖、逐項輸出辨識文件與欄位、不查知識庫，結尾提示「初步整理完成，若需進一步比對請在下一步告訴我。」），使用者確認後再進步驟二（先說「我將基於上一步的整理結果進行比對。」才查知識庫）。
- 上線前必跑：`3_驗測情境.txt` 中「純文字清單直走步驟二」與「上傳證件圖片先走步驟一」兩情境，確認步驟一未提前呼叫知識庫。

## 4. 權限與工作室設定
建議掛在「工作室4_審查比對」。KYC 文件含高度個資，屬最敏感資料，建議：
- 僅開放實際處理開戶收件的臨櫃與作業單位。
- 明確標示「僅做初檢、不做准駁」，避免使用者誤用為核准依據。
- 課堂展示與測試一律使用虛構文件，嚴禁上傳真實證件影像。

## 5. 上線前驗測 Checklist
執行 `3_驗測情境.txt` 所有情境，並確認下列 pass/fail gate：
- [ ] **情境（純文字清單直走步驟二）**：正確判定個人／法人並列出待補文件。
- [ ] **情境（上傳證件圖片先走步驟一）**：步驟一只輸出辨識結果、未呼叫知識庫，步驟二才比對。
- [ ] **防捏造 gate**：客戶未提供的文件不得標為「已收」；涉及真偽與准駁一律標「需人工複核」。

## 6. 上線後監控指標（首 2 週）
- 每日使用次數與使用者數。
- 兩階段是否正確分流（步驟一誤呼叫知識庫的次數）。
- 使用者回報「漏列待補」或「誤判已收」的次數與平均回應時間。

## 7. 異常處理與回退方案
- 若步驟一提前查知識庫，回頭檢查兩階段設定與提示詞是否被覆蓋。
- 證件影像模糊導致辨識錯誤時，請使用者改以文字清單提供。
- 維運窗口：建議由法遵／作業單位指派 owner，提示詞調整須回測上述兩個兩階段情境與防捏造情境。

## 8. 種子團隊接手提示
最常見的調整方向是「必備文件清單」與「需人工複核判準」的更新。本 Agent 可與「合約條款初步檢查助手」共用同一套條件式兩階段結構，若要新增類似的讀圖初檢 Agent，可直接以本 Agent 為起點複製。上游為臨櫃收件，下游為人工 KYC 審核與准駁。

### 情境 #9：純文字清單直走步驟二

**輸入描述**

> 貼上個人開戶已收文件清單（test_data 10）。

**預期輸出**

> 略過步驟一，判定個人開戶，列出第二身分證明文件、通訊地址證明為待補，涉及身分真偽標需人工複核，並提示僅初檢不做准駁。

**驗證重點**

> 純文字直接進入步驟二比對，正確列出待補與需人工複核。

### 情境 #10：上傳證件圖片先走步驟一再步驟二

**輸入描述**

> 上傳身分證正面影像（test_data 12）。

**預期輸出**

> 步驟一只讀圖、逐項輸出辨識到的文件與欄位、不查知識庫，結尾提示「初步整理完成，若需進一步比對請在下一步告訴我。」；使用者確認後步驟二先說「我將基於上一步的整理結果進行比對。」再對照清單。

**驗證重點**

> 步驟一未呼叫知識庫、兩階段提示語正確、隔離成立。

### 情境 #11：防捏造（法人缺件不臆測已補）

**輸入描述**

> 貼上法人開戶已收文件清單（test_data 11）。

**預期輸出**

> 判定法人開戶，列出有權簽章人清單、實質受益人聲明為待補，不假設客戶已另行提供，實質受益人相關標需人工複核。

**驗證重點**

> 未提供的文件不標為已收，如實列待補。
