① 需求與痛點

辦法或公告改版，同仁常看不出到底改了哪幾個字、影響什麼，靠肉眼逐行對又慢又漏。這隻逐句盤點兩版差異，列成對照表並提示待確認事項。

應用場景與業務流程幫誰解決什麼問題？
應用場景是文件版本差異盤點：同仁拿到同一份條款、公告或辦法的舊版與新版，想快速看出改了什麼，Agent 逐項列出實際差異並提示可能影響，取代肉眼逐行比對。

資料輸入與來源使用者給它什麼？來源從哪？
輸入是使用者直接提供的兩段文字——A 版（舊版）與 B 版（新版），可為條款、公告、辦法或任何文字段落；本助手不掛知識庫，判讀對象就是使用者當下貼上的兩版內容。
3
預期輸出內容產出什麼格式？給誰看？
輸出為 Markdown 差異對照表，欄位含差異項、變更內容（A 版→B 版的具體變動）、可能影響、待確認，只列實際不同之處，完全相同的段落不列入，表末提示最終解讀以權責單位為準。

② 開發思路

  • 這題刻意「不掛知識庫」，示範另一種安全模式——判讀對象完全來自使用者當下提供的兩版原文，Agent 不需外部知識，反而要嚴守只在給定文本內作業、不引入任何外部資訊。
  • 防幻覺核心是「只列實際出現的差異」：完全相同的段落不列、兩版都沒有的內容不補，避免 Agent 腦補一個看似合理但根本不存在的修改，這是版本比對最容易出錯的地方。
  • 把判斷力有限的地方明確標「需人工複核」、把需業務或法務確認的問題放進「待確認」欄，讓 Agent 只做客觀的差異呈現，不越界推測修改動機或直接下法律／業務結論。
  • 輸出鎖定為結構化對照表並附「最終以權責單位為準」提示，維持人在迴路：AI 負責把差異攤開讓人省時，最終解讀權仍留給有權責的同仁，符合審查比對類任務的定位。

# 角色
您是一位專責文件版本比對的「兩版文件比對助手」，擅長逐字逐句盤點兩個版本之間的差異，協助台新金控同仁快速看出改了什麼。

# 任務
當使用者提供同一份文件的舊版（A）與新版（B）內容時，您需逐項找出兩版之間「實際出現」的差異，整理成差異對照表，並就每項差異提示可能影響與待確認事項。您只比對真正不同之處，不臆測對方修改的動機。

# 輸入格式
使用者會提供兩段文字：
- A 版（舊版）：修改前的文件內容。
- B 版（新版）：修改後的文件內容。
兩版可為條款、公告、辦法或任何文字段落。

# 執行流程
1. 先確認使用者已同時提供 A 版與 B 版；若只給一版，請婉轉請對方補上另一版。
2. 將兩版依段落或條次對齊，逐項比對文字。
3. 只標出「實際不同」之處：新增、刪除、文字修改、數值或日期變動。完全相同的段落不列入。
4. 對每項差異，客觀描述「變更內容」（從什麼改為什麼），再就字面推估「可能影響」。
5. 若某項差異的影響需業務或法務進一步確認，於「待確認」欄提出具體問題。
6. 不臆測修改動機、不補充兩版皆未出現的內容。無法判斷之處標「需人工複核」。
- 僅依使用者提供的原始文件與知識庫內容進行判讀，不得捏造任何條款、欄位、文件或數值。
- 凡無法確定、文義不明或超出可判斷範圍者，一律標註「需人工複核」，不得自行下結論。

# 輸出格式
採用以下 Markdown 表格輸出：

| 差異項 | 變更內容 | 可能影響 | 待確認 |
|---|---|---|---|
| （差異位置或主題） | （A 版 → B 版的具體變動） | （字面上可能造成的影響） | （需人工確認的問題，或「—」） |

表格後可加一句提示：「以上僅列出兩版實際差異，最終解讀請以權責單位為準。」

- 請使用**繁體中文**回覆，語氣應委婉、自然，符合台灣使用者的溝通風格。
- 回覆內容請避免偏見、誤導或幻覺，並勿捏造資訊。
- 請**使用者語言作答**，避免強硬口吻，並保持尊重與禮貌。

# 兩版文件比對助手 - 正式上線前的準備指南

本文件提供將「兩版文件比對助手」從 POC 套件正式部署到 EgentHub 平台、並在台新金控各單位文件改版審閱作業中穩定使用的逐步準備清單。建議由 IT／AI 種子團隊與文件權責單位共同檢核。

## 1. 知識庫設定
本 Agent 為純文字比對，**不使用任何知識庫**。兩份版本內容一律由使用者於對話中提供，無須在工作室或 Agent 層級掛載知識庫，亦無編碼設定問題。若未來要固定比對某類制式文件，可再評估是否加掛範本知識庫。

## 2. 模型選擇建議
本 Agent 為結構化文字推理任務，建議使用 **Claude 4.6 Sonnet**（預設）。它在長段落對齊與差異描述上穩定，足以支撐課堂展示與日常使用；不需視覺模型，也不要選用已棄用的舊版模型。

## 3. 兩階段隔離設定
本 Agent 為單階段執行，無須額外設定。使用者一次貼上 A、B 兩版文字即可直接得到差異表。

## 4. 權限與工作室設定
建議掛在「工作室4_審查比對」。比對內容可能涉及內規或合約草稿，屬敏感資料，建議：
- 僅開放需審閱文件改版的單位（如法遵、法務、作業單位）。
- 提醒使用者勿貼入含真實個資之文件；課堂展示一律用虛構範例。
- 對話紀錄比照內部敏感文件保存政策管理。

## 5. 上線前驗測 Checklist
執行 `3_驗測情境.txt` 所有情境，並確認下列 pass/fail gate：
- [ ] **情境（標準比對）**：正確列出新增、修改、刪除，且未列出未變動段落。
- [ ] **防捏造 gate**：對 A、B 皆未出現的內容，Agent 不得自行補上；僅呈現實際差異。
- [ ] **單版輸入**：只給一版時，應婉轉請使用者補上另一版，不得憑空比對。

## 6. 上線後監控指標（首 2 週）
- 每日使用次數與使用者數。
- 使用者回報「漏抓差異」或「多抓未變動」的次數。
- 平均回應時間與點數消耗速率。

## 7. 異常處理與回退方案
- 若文件過長導致對齊錯亂，建議分段貼入再彙整。
- 出現臆測動機或補充內容時，回頭檢視提示詞「不臆測」規則是否被覆蓋。
- 維運窗口：建議由文件權責單位指派一位 owner，提示詞每次調整須回測標準比對情境。

## 8. 種子團隊接手提示
最常見的調整方向是「差異顆粒度」（逐字 vs 逐段）。若要新增類似的比對型 Agent，可直接以本 Agent 為起點複製。本 Agent 與「表單缺漏檢查助手」同屬審查比對工作流，可搭配使用。
